# 开发总结：从零到一学到了什么

> 面向：自己。
> 写给半年后已经忘了细节的我，所以只记结论和判断标准，不记操作步骤。

---

## 一、对"软件"的理解变了

以前：软件 = 程序。

现在：软件 = 程序 + 环境 + 身份 + 数据 + 权限 + 系统接口。

这个项目里最花时间的部分，全都落在等号右边。

## 二、Windows 这边学到的

不是"学了几个命令"，而是几个以前不知道存在的层面：

- **AppX / MSIX 包**：商店应用不在 `Program Files` 的普通目录里，要先用 `Get-AppxPackage` 找到真实安装位置。
- **环境变量当启动参数**：`CODEX_HOME` 这类变量决定程序读哪份配置，所以"开两个实例"本质上是"用两组环境变量开两次"。
- **Chromium 层的用户数据目录**：桌面应用里往往嵌着一个浏览器内核，`--user-data-dir` 决定它的登录态和缓存放哪。
- **AppUserModelID**：决定任务栏图标是否合并。这个字段平时完全感知不到，直到你需要两个独立图标。
- **进程树**：关窗口不等于退出程序，要按父子关系把整棵树找出来再关。
- **沙箱与 ACL**：`WRITE_DAC` 这种权限平时用不到，缺了它会让整个沙箱停摆，而报错信息完全看不出是权限问题。

## 三、对 Agent 的理解变了

Agent 不等于聊天机器人。差别在结构上：

```
目标 → 规划 → 执行 → 反馈 → 调整
```

聊天机器人只有"问 → 答"，缺的正是后面三步：状态存在哪、谁执行、执行结果怎么回到决策者手里。

这个项目里，那三步靠三个文件（`PLAN.md` / `RESULT.md` / `REVIEW.md`）落地，而不是靠一个框架。这是刻意的选择：**先验证协议，再写调度**。协议不对，框架只会把错误放大。

另一个反直觉的结论：**协议里最关键的字段是"验收标准"**。没有它，审查者只能凭感觉说"差不多"；有了它，判断才能变成逐条核对 PASS / FAIL。设计系统时，定义"怎么算完成"往往比定义"要做什么"更值钱。

## 四、工程思想上的几条

**1. 能跑通不等于做完了。** 我的环境跑了好几个月，但安装脚本丢了之后，它就没法在第二台机器上重建。真正的完成标准是：别人能装、别人能看懂、别人能复现。

**2. 先收集，再重构。** 已经验证能用的代码是资产。重构之前先原样收进项目、记录来源和哈希，改的时候才知道自己动了什么。

**3. 报错信息经常指错方向。** 沙箱那个例子里，报错长得像网络问题，根因是目录权限。看到报错先别按字面修，先问"这个报错是在哪一层产生的"。

**4. 把踩坑写下来是工程的一部分，不是副产品。** 同一个坑我踩过两次，第二次才想起"这个好像见过"——因为第一次没写。

**5. 环境隔离问题的本质是"状态放在哪"。** 一个程序的状态散在配置、缓存、数据库、系统身份里，只要有一处共用，隔离就不成立。找隔离方案，其实就是把所有存放状态的地方列一遍。

## 五、如果重来一次，我会怎么改

- 从第一天就写安装脚本，并且**把安装脚本本身放进版本控制**（我这次丢的就是它）。
- 手写的配置项立刻标注"哪些是必需的、哪些是自动生成的"，不然后来根本分不清。
- 每解决一个环境问题，当场记一行根因——不是记操作步骤，是记"为什么"。
- 更早地把"别人的机器"当成验收环境：只在自己机器上跑通，等于没验证。

## 六、下一步想做的事

- 写一个真正的安装器：检测环境 → 建目录 → 写配置 → 装启动器 → 健康检查。
- 写卸载，能干净移除这两个环境。
- 让协作协议的推进少一点人工搬运：至少做到"检测到 PLAN 就提示该谁干活"。
- 再往前走，是把这套东西套到真实项目上跑（游戏、论文），看协议在真实压力下哪里先崩。
